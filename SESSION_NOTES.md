## What this is

A Rayfield-Gen2-shaped Roblox UI library (`CreateWindow` → `CreateTab` → `CreateToggle`/`Slider`/`Dropdown`/`MultiDropdown`/`Input`/`Keybind`/`ColorPicker`/`Button`/`Label`), skinned in an Apple HIG dark-mode + glassmorphism look. ## Bugs found and fixed this session (all applied to `library.lua`)

1. **Duplicate windows on re-run.** `CreateWindow` used to just create a new `ScreenGui` every call with no cleanup — re-executing the script stacked windows on top of each other (looked like "the previous tab won't disappear," but was actually two whole separate windows overlapping). Fixed: `CreateWindow` now destroys every existing `IOSRobloxUILib` child in the gui parent before creating a new one.
2. **Square corners on the dock side.** `ClipsDescendants` on the outer `sheet` only clips to a rectangular bounding box — it does **not** respect a sibling's `UICorner` shape. The `dock` frame (flat rectangle, different color from `sheet`) poked sharp corners through the sheet's rounded silhouette. Fixed: gave `dock` its own matching `UICorner(Radius.Sheet)`.
3. Icons were empty placeholders → replaced with hand-built zero-asset vector glyphs (`IconBuilders.terminal/stack/sliders/dot` in `library.lua`), tinted active/inactive via `tintIcon()`. Numeric `rbxassetid` icons still supported as a fallback path.
4. Added the round dock-collapse toggle button (floats on `sheet`, not `dock`, so it survives collapse). Spec lives in `MASTER.md` §7.
5. **Dropdown flyout rendered underneath later rows (e.g. a `Test Button` below it).** Root cause: `screenGui.ZIndexBehavior` was `Sibling`, which scopes ZIndex comparisons to same-parent children only. The dropdown's flyout list (`ZIndex = 10`/`11`, nested inside its own row) and the dock-toggle glyphs (`ZIndex = 25-27`) were both written assuming *global* stacking, but under `Sibling` those numbers never got compared against an unrelated branch (a different row) — draw order fell back to child/creation order instead, so a later row could paint over an open dropdown regardless of its ZIndex. Fixed: `ZIndexBehavior` → `Enum.ZIndexBehavior.Global` (`library.lua` line ~298). Verified live via `execute-file` smoke test (Fly Hack toggle / Speed slider / Mode dropdown forced open / Test Button) — flyout now correctly draws on top. Screenshot confirmed via the MuMu emulator window (see capture workaround below).
6. **Clicking a dropdown option (e.g. "Noclip") also fired whatever was underneath the flyout (e.g. "Test Button").** First attempt: gave the flyout `list.Active = true` (Frames default `Active = false`, which doesn't block clicks to whatever they visually overlap). **This did NOT actually fix it** — user sent a screen recording re-testing with the `Active = true` build, still reproduced (Test Button fired when clicking Noclip). Real root cause: the flyout was nested *inside its own row* (parented to `btn`, inside `Row3`), which put it in the same branch of the instance tree as every other row, including Test Button's (`Row4`). Even fully-Active GuiButtons in sibling rows could apparently still both register a single click in that structure — `Active`/ZIndex tuning wasn't enough to fully separate them. **Real fix:** added a dedicated top-level `Overlay` frame (`Window.Overlay`, a child of `sheet`, created in `CreateWindow`) that floating UI parents into instead of nesting inside a row. `CreateDropdown`'s `list` now parents to `overlay`, not `btn`, with its position computed fresh on every open via `positionList()` (`btn.AbsolutePosition`/`AbsoluteSize` converted to overlay-local pixel offsets, since it no longer inherits `btn`'s position for free). This makes the flyout a fully separate branch from every row — there's no other row's button anywhere "behind" it in the tree for a click to also land on. `list.Active = true` kept as a belt-and-suspenders second layer. Also added in this pass (kept from the first attempt): the flyout animates open/close (height 0→full + fade, `Motion.Tab`, 160ms Quad Out) instead of an instant `Visible` flip, and the currently-selected option highlights in `AccentBlue` while open. New motion entries logged in `MASTER.md`. User confirmed live: **this one actually holds** — dropdown/Test Button conflict is gone.

7. **Regression: after fix #6, Fly Hack toggle stopped toggling and Test Button stopped responding/animating.** User caught this via real testing. Investigation used synthetic clicks (`mousemoveabs`/`mouse1click`, confirmed present in this executor) to try to reproduce it live — but a **control test on a completely bare `TextButton`, no window/library code involved at all, also failed to register a synthetic click**, proving the synthetic-click test method itself is unreliable in this environment (probably tracks the real OS cursor rather than actually warping it, so the earlier "verified with a real click" claim for bug #6 was likely a false positive from the user's own cursor happening to already be near the target, not real proof the tool works). Stopped trusting synthetic clicks as verification for the rest of this session.

   First attempted fix: reordered so `overlay` (added in bug #6) is created *before* `content` in `sheet`'s children, reasoning that `ZIndexBehavior.Global` breaks same-default-ZIndex ties by insertion order (later child wins) and `overlay` — created after content originally — may have been winning that tie and silently eating all clicks to content. **User confirmed live: this fixed the toggle/button regression.** But then:

8. **Regression: fixing #7 un-fixed #6** — user reported the dropdown-vs-Test-Button double-click conflict was back after the overlay/content reorder. This confirms the insertion-order tie-break theory from #7 was right, but also proves insertion order is not a safe knob to turn: overlay-after-content fixes #6 but breaks #7; overlay-before-content fixes #7 but un-fixes #6. They were never independent — flipping the order just traded one bug for the other. **Real fix:** stopped relying on insertion-order ties entirely. Gave `overlay` an explicit `ZIndex = 0` (below content's default `1`), so `overlay`'s own (invisible) body can never win input priority over `content` regardless of creation order — while a flyout's `list` (explicit `ZIndex = 10`, a child of `overlay` — children don't inherit a parent's ZIndex in Roblox) still unconditionally draws/receives input above content whenever it's actually open, since `10 > 1` regardless of order either way. This should be deterministic in a way the previous two attempts weren't. Verified only: zero runtime errors, and live property check confirms `Overlay.ZIndex == 0` while Toggle's `Track` and Test Button's own button both sit at the default `1` — **not yet confirmed by the user's own test**, since synthetic clicks aren't trustworthy here. This is the third attempt at this specific class of bug (rows #6/#7/#8) — flag to the user if a fourth surfaces, might mean the whole "shared overlay" approach needs rethinking rather than another tweak.

9. **Real fix for the dropdown-vs-Test-Button click-through, found via the user's actual physical tap-test (screenshot: dropdown open, tapping "Noclip" also fired Test Button, and Noclip sometimes failed to select at all).** Root cause was different from bugs #6/#7/#8: `list` (the flyout background Frame) had `ZIndex = 10`, but the individual clickable option buttons (`opt`, the actual `TextButton` per option, `CreateDropdown` ~line 936) were created with **no explicit ZIndex**, defaulting to `1`. 10. **Dock-collapse animation visually "detached" into what looked like a separate floating frame mid-tween.** User reported this from a phone screenshot; a synthetic instant-collapse probe (no tween, just snapping the end-state values) looked totally clean, which pointed at something transient happening only *during* the animation rather than a resting-state layout bug. Root cause: `dock`'s `UICorner` used a fixed 20px radius on all 4 corners (from bug #2's fix), but only the left two corners are ever near the sheet's rounded silhouette — the right two are a purely internal seam against `content` and never needed rounding. As `dock.Size.X` tweens down toward 0, a fixed 20px radius on a frame narrower than 40px forces Roblox to render it as a shrinking rounded pill/blob for the last stretch of the animation, which reads as a separate floating rounded shape detaching from the sheet. Fixed: captured the dock's `UICorner` as `dockCorner` and added a parallel tween on `CornerRadius` (20 → 0 closing, 0 → 20 opening) alongside the existing width tween, so the radius never exceeds half the frame's current size. Verified: smoke test loads clean, no runtime errors. **Not yet confirmed by the user actually watching the collapse animation** — that's the next thing to check.

11. **Dock read as a visually separate rounded panel "bolted onto" the sheet, not one continuous frame — this was the deeper issue behind the user's "coming from outside the main frame" report, distinct from bug #10's animation-only blob.** Two more zoomed user screenshots (dock open, resting state) made it clear: `corner(dock, Radius.Sheet)` rounds all 4 corners of `dock`, but the right two sit against `content` deep inside the window, nowhere near the sheet's outer edge — rounding them made `dock` render as its own independently-rounded rectangle. Fixed: added a same-color (`Colors.BgDock`) flat-cornered `RightSquareOff` patch frame, `Radius.Sheet` px wide, full height, positioned at `dock`'s rightmost strip (`Position = UDim2.new(1, -Radius.Sheet, 0, 0)`), parented inside `dock` after the corner. It paints over the right corners' curve so only the left two corners (the ones actually flush against the sheet's own rounding) stay visibly rounded. Verified: smoke test loads clean; self-captured screenshot (PowerShell/MuMu workaround) shows the dock/content boundary as a clean straight seam instead of a curved notch. **Not yet confirmed by the user's own eyes on the real device** — downscaled tool screenshots may miss subtle mismatches they'd catch directly.

12. **Regression from bug #11's own fix: tab slots rendered misaligned (dot pushed to the bottom of the dock instead of under the menu button)**, caught immediately by the user in their next round of screenshots. Root cause: `RightSquareOff` (added directly to `dock`) was a sibling of `dock`'s `UIListLayout` — and `UIListLayout` arranges *every* GuiObject child of its parent regardless of intent, no "ignore this one" flag exists. `RightSquareOff`'s full-height (`Size.Y.Scale = 1`) got treated as a giant first list item (default `LayoutOrder = 0`, sorts first), shoving the real tab slot down past it. Fixed: introduced a nested `DockList` frame (`dock`'s child, full-scale, transparent) that now owns the `UIListLayout` and top/bottom padding; tab slots parent into `Window.DockList` instead of `Window.Dock`. `RightSquareOff` stays a direct child of `dock`, a plain sibling of `DockList`, invisible to the layout. Verified live via `get-data-by-code`: single-tab slot sits at relative Y=46 (matches top padding, not the bottom); a two-tab smoke test showed slots stacking correctly at Y=46 and Y=86 (46 + 32px slot + 8px gap). **Not yet confirmed by the user's own eyes** — screenshot tooling on this machine is currently unreliable (the local terminal window keeps landing on top of the MuMu capture region), so this was verified structurally via instance-position probes rather than visually. ## Verification session (Aug 29) — bugs #10, #12, #14 confirmed live

Found a reliable way to click-test this library after all: `getconnections(button.SomeClickSignal)` returns the real connected Lua callbacks in this executor, and calling `:Fire()` on one of them invokes it directly — no cursor/input simulation involved, so it doesn't inherit the synthetic-click unreliability from bug #7. Sanity-checked against Test Button's `print` callback (showed up in `get-console-output`) before trusting it for anything else.

Workflow gotcha that cost real time and produced a false-negative — **flag this to any future session**: this executor's Roblox client is a *persistent* process across separate `get-data-by-code` calls, and `CreateWindow`'s `Window` Lua table (with its `ActiveTab`/`CloseActiveFlyout` state) lives across those calls too. `CreateTab`'s `activate()` early-returns with no side effects when `self.ActiveTab == Tab` (switching to the tab that's already active) — so a test script that fires a tab-slot click assuming it'll trigger a real switch, when a *previous, separate* tool call already left that tab active, silently no-ops and never calls `CloseActiveFlyout`. This produced an apparent repro of bug #14 (flyout not closing on tab switch) that was actually just leftover state from an earlier probe having already consumed the switch. Fix for the *method*: either re-`execute-file` the smoke test fresh (resets `CreateWindow`'s state completely — it destroys and rebuilds the whole window) before a bug-specific test, or do the whole open→switch→check sequence in one single `get-data-by-code` call so there's no gap for a prior call's residual state to interfere.

Also re-confirmed the sibling behavior (opening one flyout closes another already-open one) still holds: opened Visuals' ESP MultiDropdown, then opened Aura Color's ColorPicker without closing ESP first — ESP's list closed automatically (`Visible` true→false, size collapsed).

- **Bug #11 (right-corner seam / `RightSquareOff`) and #12 (tab alignment): confirmed structurally, resting state.** `RightSquareOff` present, positioned at `{1,-20},{0,0}` inside `dock` (flush against the right edge, patching the corner as designed). 15. **Real bug, found by the user's own physical testing right after the above: reopening a dropdown/multidropdown/colorpicker that had auto-closed (e.g. by a tab switch) left it permanently stuck — visually open forever, unresponsive to clicking an option OR re-tapping the box to close it.** Root cause was a reentrancy bug in all three flyout widgets' shared `setOpen` pattern (`library.lua`, Dropdown ~1309, MultiDropdown ~1614, ColorPicker ~1947): `open = value` was set to `true` **before** calling `self.Window.CloseActiveFlyout()`. If this exact widget was still the last-registered "active" closer (true whenever nothing else opened a flyout in between — e.g. right after a tab-switch auto-close), reopening it called `CloseActiveFlyout()`, which was still pointing at *this same widget's own* closure from last time (`function() if open then setOpen(false) end end`) — and by then `open` was already `true`, so it invoked its own `setOpen(false)` on itself, mid-open. That flipped the shared `open` upvalue back to `false` while the code kept running the "open" branch regardless (already past the `if open then` check), so the list ended up visually open (`Visible=true`, full size) with its internal `open` flag permanently reporting `false`. Every later tap on the box called `setOpen(not open)` = `setOpen(true)` again — which hit the exact same self-close reentrancy every time — so it could only ever replay "open," never reach the real close branch.
